## 1. 背景与问题

当前工坊主要通过一次模型调用，根据自然语言直接生成工具。该方式适合简单、低风险、单文件工具，但在以下场景中可靠性不足：

- 工具需要多个文件、测试或依赖；
- 输入、输出和异常行为没有被明确建模；
- 生成后无法根据测试失败继续修改；
- 文件、网络、剪贴板和命令执行权限不清晰；
- 生成结果未经独立验证就可能进入正式工具目录；
- 用户无法在 Agent 遇到产品决策时进行澄清。

本功能的目标不是简单替换一个更强的模型，而是为复杂工具提供完整的、可控的构建和交付流程。

## 2. 产品定位

新增 **工坊高级生成** 模式，保留现有快速生成模式。

高级生成的职责分工如下：

- **Nemo**：需求确认、权限边界、临时工作区、构建生命周期、用户干预、产物验证、安装、禁用、回滚和审计；
- **Claude Code 或 Codex**：读取规格和模板，在临时工作区内自主探索、编码、测试、分析失败原因并修复实现。

Nemo 不复制一套完整的编码 Agent Loop，也不把功能做成通用 PowerShell 或任意 `exec` 客户端。外部编码 Agent 的价值在于自主完成多文件开发循环，而不是只返回一段代码。

完整流程：

```text
用户描述需求
    ↓
Nemo 整理 ToolSpec
    ↓
用户确认需求、权限上限和验收标准
    ↓
Nemo 创建临时构建工作区
    ↓
外部编码 Agent 自主探索、编码、测试和修复
    ├── 需要澄清 → 等待用户回答后继续
    ├── 用户取消 → 终止构建
    └── 完成 → 返回构建结果
    ↓
Nemo 独立验证协议、权限、依赖和实际行为
    ↓
用户查看 diff 和验证报告
    ↓
用户确认后安装到正式工坊
```

## 3. 目标与非目标

### 3.1 目标

1. 让复杂工具由外部编码 Agent 自主完成多文件实现、测试和修复。
2. 让 Nemo 在生成结果进入正式工坊前掌握权限和质量控制权。
3. 让用户在需求歧义、权限变化和关键产品决策处能够干预。
4. 让构建失败、取消、超时和安装失败拥有明确且可恢复的状态。
5. 保持现有快速生成流程可用，并让两种模式经过一致的安装和运行时策略。
6. 为未来接入第二个编码 Agent 保留适配边界，但不在第一版同时实现多个外部后端。

### 3.2 非目标

第一版不包含：

- 内嵌 PowerShell 或完整终端；
- 通用 `exec` 输入框；
- 对用户任意项目进行编码；
- 自动 Git commit 或 push；
- 自动上传代码或工具源码；
- 多个 Agent 并行协作；
- 完整 IDE、文件树或通用代码编辑器；
- 无限自动修复循环；
- 系统级剪贴板、收集箱、智能粘贴或命令面板；
- 让生成工具绕过现有 `ToolRegistry` 和安全策略。

## 4. 用户流程

### 4.1 选择生成模式

工坊提供两个入口：

- **快速生成**：沿用现有单次模型生成流程，适合简单、低权限工具；
- **高级生成**：进入规格确认、外部 Agent 构建、验证和安装审核流程。

高级生成入口需要说明：构建会在临时目录中运行，可能调用本机已经安装和认证的外部编码 Agent。

### 4.2 描述工具需求

用户提供自然语言需求，并填写必要的边界信息：

- 工具名称或期望名称；
- 工具用途；
- 输入方式和输出格式；
- 是否需要读取或写入文件；
- 是否需要网络；
- 是否需要读写剪贴板；
- 是否需要 Shell、子进程或外部程序；
- 其他已知约束。

表单不要求用户编写完整技术设计，但必须帮助 Nemo 区分产品需求和权限需求。

### 4.3 规格确认

Nemo 使用现有模型将需求整理为结构化 `ToolSpec`，并展示以下内容：

- 工具名称和用途；
- 输入参数及类型；
- 输出格式；
- 异常行为和边界情况；
- 所需权限；
- 依赖和运行时要求；
- 验收标准。

用户可以确认、返回修改需求、直接编辑允许编辑的规格字段，或取消。只有用户确认后，才创建工作区并启动外部 Agent。

### 4.4 选择构建后端

第一版只实现一个外部编码 Agent 适配器。具体选择应以实施开始时用户已安装、已认证且支持自动化工作目录的后端为准，不能同时把 Claude Code 和 Codex 都纳入第一版交付范围。

Nemo 不要求用户填写任意命令行模板。后端的可执行文件、固定参数、版本检测和能力声明由适配器配置管理。

后端不可用时，界面必须说明具体原因，例如未安装、未认证、版本不支持或不具备所需的恢复能力，并允许用户返回快速生成或取消。

### 4.5 构建过程

构建页面展示：

- 当前状态和阶段；
- 构建后端和版本；
- 已耗时；
- 经过脱敏的实时日志；
- 当前文件变更；
- 测试状态；
- 用户澄清请求；
- 暂停和取消操作。

Nemo 不逐步指挥 Agent 修改哪个文件。Agent 在工作区内自主完成探索、编码、测试和修复。

### 4.6 验证与安装审核

构建完成后，Nemo 独立验证：

- manifest 和入口是否有效；
- 参数 Schema 是否正确；
- 必需文件是否存在；
- 测试是否通过；
- 依赖是否声明；
- 实际权限是否超出批准范围；
- 是否出现明显危险行为；
- 是否符合现有工坊运行协议。

结果页展示构建摘要、文件 diff、测试结果、权限和依赖、阻断问题及警告。只有用户明确确认“安装并启用”后，经过验证的产物才进入正式工具目录。

## 5. 用户干预与澄清

高级生成不是不可干预的后台任务。第一版支持三类用户控制。

### 5.1 随时取消

用户可以请求暂停或取消构建。取消时 Nemo 必须：

- 请求外部 Agent 退出；
- 等待退出并在必要时终止整个子进程树；
- 将最终状态记录为 `cancelled`；
- 允许用户保留工作区和日志，或明确清理；
- 不能把部分生成结果标记为成功或可安装。

### 5.2 Agent 主动请求澄清

当 Agent 发现以下情况时，不能自行猜测或扩大权限：

- 需求有多种合理解释；
- 需要新增权限；
- 需要新增外部依赖；
- 需要改变已确认的输入或输出行为；
- 验收标准互相冲突；
- 需要访问真实外部服务或敏感数据；
- 可能覆盖已有工具；
- 无法在当前权限上限内完成需求。

Agent 应通过后端支持的结构化事件或约定文件提出问题。Nemo 向用户展示问题、上下文、可选方案、推荐方案以及对行为和权限的影响。用户回答后，Nemo 将回答交还给同一构建任务继续执行，并把决策写入构建记录。

### 5.3 用户主动指导

第一版允许用户在明确的暂停点：

- 补充需求；
- 要求增加测试；
- 要求解释当前方案；
- 指定实现方向；
- 要求修复验证问题。

第一版不承诺支持任意时刻向正在运行的外部 CLI 插入文本。实时终端式交互依赖 ConPTY/PTY、ANSI、输入焦点和会话恢复能力，属于后续能力。

### 5.4 后端能力差异

适配器必须声明后端能力：

```text
supports_streaming
supports_cancel
supports_resume
supports_structured_events
supports_user_questions
supports_permission_requests
```

如果后端只支持非交互执行，Nemo 只能可靠提供启动、日志、完成、失败、超时和取消；遇到歧义时应结束或暂停为待处理结果，由用户修改规格后重新构建。Nemo 不能通过解析普通日志中的问号来假定 Agent 正在提问。

## 6. 核心模块与职责边界

```text
高级生成 UI
    ↓
ToolBuildService
    ├── ToolSpec
    ├── BuildWorkspace
    ├── ToolBuilderBackend
    │      └── ProcessRunner
    ├── PermissionPolicy
    ├── ToolValidator
    ├── ToolInstaller
    └── BuildReport
            ↓
        ToolRegistry
```

### 6.1 `ToolSpec`

保存用户确认后的需求、权限上限和验收标准。它是生成和验证的共同输入。外部 Agent 可以补充内部实现细节，但不能扩大用户确认的权限。

### 6.2 `ToolBuildService`

负责准备规格和工作区、启动外部 Agent、转发状态和日志、处理取消和澄清、等待 Agent 完成、收集结果并触发独立验证。它不负责逐文件编写代码，不负责复制完整 Agent Loop，也不代替外部 Agent 修复普通编码错误。

### 6.3 `BuildWorkspace`

为每次构建创建独立目录，保存规格、模板、源文件、测试、日志和验证报告。正式工具目录不能作为外部 Agent 的工作目录。

### 6.4 `ToolBuilderBackend`

为 Claude Code、Codex 等外部 Agent 提供统一生命周期适配。至少需要处理可用性检测、认证状态、版本、启动、事件、取消、恢复能力和结果收集。

### 6.5 `ProcessRunner`

这是唯一允许启动外部编码 Agent 的底层模块。它使用可执行文件路径、固定参数数组、明确工作目录和白名单环境变量，不提供通用 Shell 字符串执行接口。

### 6.6 `PermissionPolicy`

管理构建权限、用户批准的工具运行权限和运行时策略。构建时允许外部 Agent 修改临时工作区，不代表生成工具自动获得同样的运行能力。

### 6.7 `ToolValidator`

由 Nemo 独立执行协议、权限、依赖、入口和危险行为检查。外部 Agent 的自评、构建说明或自生成报告不能替代 Nemo 的验证结果。

### 6.8 `ToolInstaller`

只安装白名单和验证通过的产物，保护旧版本，处理同名冲突，尽量使用原子替换，并在失败时清理半成品或恢复旧版本。

### 6.9 `BuildReport`

保存规格、后端、版本、状态、文件摘要、测试结果、检测到的权限、问题、澄清记录、安装决策和审计信息。日志必须脱敏，不记录 API 密钥、完整环境变量或不必要的敏感文件内容。

## 7. 构建协议

### 7.1 `ToolSpec` 内容

协议至少包含：

- `schema_version`；
- 工具标识、显示名称和描述；
- 输入参数、类型、是否必需和说明；
- 输出类型和说明；
- 权限上限；
- 允许依赖或运行时要求；
- 验收标准。

输入类型和权限必须来自 Nemo 支持的有限集合，不能允许模型自由发明运行时能力。

### 7.2 `manifest`

生成工具必须提供机器可读清单，至少描述：

- manifest 版本和工具 ID；
- 入口文件和函数；
- 描述；
- 输入 Schema；
- 权限；
- 运行时和依赖。

验证器必须比较 `ToolSpec` 与 `manifest`，确保入口、参数和权限不超过用户确认范围。

### 7.3 权限枚举

第一版权限集合应保持有限且可审计，至少区分：

```text
file_read
file_write
network
clipboard_read
clipboard_write
shell
python_subprocess
process_spawn
```

文件读取与写入、剪贴板读取与写入、网络与 Shell 不能合并为一个笼统权限。权限至少需要表达未申请、已申请和已批准的状态。

### 7.4 工作区结构

工作区的概念结构如下：

```text
build-id/
├── input/
│   └── tool-spec.json
├── source/
│   ├── manifest.json
│   ├── generated files
│   └── tests/
├── logs/
│   ├── process.log
│   └── sanitized-events.jsonl
└── reports/
    ├── validation.json
    └── build-report.json
```

Nemo 生成固定的构建说明，写明入口协议、必需文件、允许依赖、测试要求和禁止修改的目录。外部 Agent 只能在约定的源目录中生成工具产物。

### 7.5 标准化事件

后端适配器应将自身输出映射为标准事件，例如：

```text
started
output
file_changed
test_started
test_finished
needs_user_input
permission_request
warning
failed
completed
cancelled
```

事件是 UI 和状态机的输入，但不能直接让外部 Agent 的文本输出改变安装状态。

## 8. 状态机

建议状态如下：

```text
draft
  ↓
spec_review
  ↓
building
  ├── waiting_for_user_input → building
  ├── paused → building
  ├── cancelled
  ├── build_failed
  └── validating
          ├── validation_failed
          └── install_review
                  ├── install_cancelled
                  ├── installed
                  └── install_failed
```

其中：

- `waiting_for_user_input`：Agent 明确提出问题并等待用户回答；
- `paused`：用户主动暂停或要求补充指导；
- `build_failed`：外部进程或构建过程失败；
- `validation_failed`：产物存在阻断问题，禁止安装；
- `install_failed`：安装失败但旧版本必须保持可用。

状态持久化是必要条件。窗口关闭或应用重启后，Nemo 必须能恢复构建记录，并且不能把未完成状态误报为成功。

## 9. 错误处理与权限验证

### 9.1 错误分类

至少区分：

- 后端未安装、未认证或版本不支持；
- 外部进程启动失败；
- 构建超时；
- 用户取消；
- Agent 异常退出；
- 工作区不可写；
- 测试失败；
- manifest 或入口无效；
- 依赖未声明；
- 检测到超出批准范围的权限；
- 安装冲突或安装失败。

每类错误都应提供明确后续动作：重试、更换后端、返回修改规格、查看工作区、查看日志、保留现场、清理或放弃。

### 9.2 权限只能收缩

权限流程必须是：

```text
需求声明
    ↓
Nemo 生成候选权限
    ↓
用户确认权限上限
    ↓
Agent 在上限内实现
    ↓
Nemo 检查实际行为
    ↓
超出上限则阻断安装
```

如果 Agent 请求新增权限，Nemo 必须展示原因、影响和风险，由用户明确批准或拒绝。Agent 不能通过修改 manifest、说明文件或构建报告自行获得权限。

### 9.3 静态检查边界

静态检查只能识别明显违规，不能被描述为绝对安全保证。至少检查：

- 禁止模块和危险 API；
- Shell、子进程和网络调用；
- 工作区外路径访问；
- 未声明依赖；
- 对协议文件的篡改；
- 明显的密钥读取逻辑；
- 绕过 Nemo 权限接口的尝试。

未批准的高风险行为必须阻断安装；无法判断的行为进入人工审查，不自动安装。

### 9.4 外部进程边界

必须：

- 使用可执行文件和参数数组，不拼接 Shell 命令；
- 设置独立工作目录；
- 使用最小化且白名单化的环境变量；
- 不暴露 Nemo 的 API 密钥、配置目录、数据库和完整数据目录；
- 支持超时、取消和子进程树终止；
- 记录程序、版本、工作目录和退出码；
- 对过程日志脱敏；
- 不自动执行登录、提交、推送或上传。

工作目录不是操作系统级沙箱。界面必须明确告知用户，外部 Agent 的实际系统权限还取决于其自身运行模式和 Windows 环境。

## 10. 测试策略

### 10.1 单元测试

覆盖：

- `ToolSpec` 解析、校验和版本兼容；
- 权限集合比较和收缩；
- manifest、入口和参数 Schema 校验；
- 状态机合法和非法转移；
- 路径边界和文件白名单；
- 日志脱敏；
- 事件解析和退出码映射；
- 构建报告生成；
- 安装失败清理和回滚。

必须验证：已批准权限不能扩大、验证失败不能进入安装、取消不能记录为成功、安装失败不能破坏旧版本。

### 10.2 后端适配器测试

使用假的可执行程序或测试替身，不依赖真实 Codex 或 Claude Code：

- 参数按数组传递；
- 工作目录正确；
- 环境变量经过白名单过滤；
- stdout/stderr 映射为统一事件；
- 退出码正确映射；
- 超时和取消能终止子进程树；
- 异常退出时保留构建现场；
- 日志敏感内容被脱敏；
- 后端能力声明影响流程行为。

### 10.3 集成测试

使用固定的模拟构建后端覆盖：

- 正常构建和安装；
- 缺少必需文件；
- manifest 格式错误；
- 测试失败；
- 未声明网络访问；
- 路径越界；
- 外部助手超时；
- 用户取消；
- Agent 请求澄清后恢复；
- 同名工具升级；
- 安装中途失败并恢复旧版本；
- 应用重启后恢复构建状态。

### 10.4 安全测试

覆盖：

- 用户需求不能注入 Shell 参数；
- 构建目录不能通过路径拼接或链接逃逸；
- 构建进程不能获得 Nemo 密钥、数据库和完整配置；
- 工具不能伪造验证报告；
- manifest 权限不能覆盖实际检测结果；
- 未批准的 Shell、网络和子进程行为必须阻断安装；
- 运行阶段仍重新执行权限检查；
- 日志不泄露 API 密钥、环境变量或不必要的敏感路径。

### 10.5 端到端测试

至少覆盖两个流程：

1. 成功流程：需求、规格确认、构建后端、Agent 自主编码和测试、Nemo 验证、diff 查看、安装并运行。
2. 失败恢复流程：Agent 生成违规权限或失败测试，Nemo 阻止安装，用户查看报告并选择修复、重试、保留现场或放弃。

自动化测试不应调用真实收费外部 Agent。真实后端只做发布前手动验收。

## 11. 分阶段实施

### 阶段 1：工坊协议和验证基础

- 确认现有工具加载、执行和目录边界；
- 定义 `ToolSpec`、manifest、权限枚举和构建报告；
- 实现确定性校验器；
- 为现有快速生成接入基础校验；
- 覆盖协议和权限边界测试。

完成标准：一个工具可以被结构化描述、校验、预览和安装，安装前不直接信任模型输出。

### 阶段 2：外部构建后端

- 实现 `ToolBuilderBackend`；
- 实现 `ProcessRunner`；
- 实现可用性、认证和版本检测；
- 实现日志、事件、超时、取消和状态恢复；
- 使用测试替身完成自动化测试；
- 只接入一个选定的外部编码 Agent。

完成标准：Nemo 能把确认后的规格交给外部 Agent，由 Agent 自主完成编码和测试，并在失败、超时或取消时正确恢复。

### 阶段 3：高级生成 UI

- 增加快速生成和高级生成入口；
- 实现需求输入和规格确认页；
- 实现后端选择和可用性提示；
- 实现构建进度、日志、澄清请求和取消；
- 实现 diff、验证报告、权限审查和安装确认；
- 保持快速生成兼容。

完成标准：用户能完成“需求 → 外部 Agent 构建 → Nemo 验证 → 用户确认安装”的完整流程。

### 阶段 4：后续增强

在前面流程稳定并有真实使用数据后，再考虑：

- 验证报告回传给外部 Agent 的有限修复循环；
- 最大修复轮数和总时间预算；
- 第二个外部编码 Agent 后端；
- 更完整的会话恢复和用户指导；
- 必要时再评估受控终端交互。

## 12. 成功标准与验收决策

功能达到可用状态必须满足：

1. 外部 Agent 能自主完成多文件编码、测试和修复，而不是只返回一段代码。
2. Nemo 没有复制一套完整的编码 Agent Loop。
3. 用户能在需求歧义、权限变化和关键决策处进行干预。
4. 外部 Agent 无法绕过 Nemo 和用户批准的权限上限。
5. 生成结果不会未经用户确认进入正式工具目录。
6. Nemo 能独立发现协议、权限、依赖和明显危险行为问题。
7. 构建失败、暂停、取消、超时和安装失败均有可恢复状态。
8. 现有快速生成流程继续可用。
9. 自动化测试覆盖核心状态、权限、进程和安装边界。
10. 系统级效率工具仍作为后续独立项目，不进入本功能交付范围。

最终产品模型为：

```text
Nemo = 工具构建治理层 + 用户控制层 + 安装交付层
Claude Code / Codex = 自主编码执行层
```
