# Nemo 内存优化方案

状态：已完成共用 HTTP 传输替代、SDK 依赖移除和启动检查优化；对象治理、真实内存复测与 OCR 进程化仍按证据推进。
日期：2026-11-12。

费用策略更新：普通应用已停用本地价格表和 LiteLLM 价格估算，仅记录服务商明确返回的费用。后续替换模型适配器无需重建价格表；保留 token 与费用来源语义即可。

实施进展：聊天、划词、截图、工具生成和咨询统一使用 httpx 与独立协议 codec。LiteLLM/OpenAI SDK、旧预热、依赖及打包收集规则均已移除；旧配置和密钥槽位兼容保留。验证仅使用离线协议和本机回环服务，不发送付费请求。下述内存数字是第一阶段历史实验，不是本次全供应商替代后的新测量。

三次受控对比：客户端就绪后专用工作集中位数 249.52 → 152.09 MiB，专用提交量 611.56 → 513.46 MiB。详见[轻量传输实现与内存验证](lightweight-model-transport.md)。

## 1. 目标与原则

降低常驻后台时的内存占用，保留划词解释的快速首次响应和已有供应商兼容性。按实测收益拆成可独立回退的改动，不一次改写整个运行时。

- 按应用进程树合计测量，包含 Python 启动器和未来可能增加的 OCR 子进程。
- 同时记录专用工作集与专用提交；两者不相加，不通过强制清空工作集制造降幅。
- 不用自动模型请求预热，不引入额外 token 消耗。
- 延迟加载改善启动占用；真正减少使用后的常驻内存，需要消除依赖、释放对象或结束持有资源的进程。
- 内存优化不改变运行记录、成本记录和评估包的职责边界。

## 2. 已有证据与限制

采样时，实际主进程专用工作集约 397 MiB，总工作集约 497 MiB，专用提交约 806 MiB；启动器专用工作集约 0.6 MiB。截图约 413 MB 与本次采样不在同一时刻，不能直接当作稳定基线。

独立进程按步骤加载的专用工作集增量估算：

| 类别 | 估算增量 |
| --- | ---: |
| Python 基础 | 7 MiB |
| Qt、Fluent、应用模块及空界面 | 75 MiB |
| tiktoken 分词器初始化 | 32 MiB |
| OCR 初始化及依赖 | 40–43 MiB |
| LiteLLM SDK 及依赖 | 约 96 MiB |
| 实际进程超过空界面实验的差额 | 约 145 MiB，尚未归因 |

OCR 与 SDK 使用两种加载顺序交叉测量，增量相近。空界面总计约 252 MiB；执行一次合成 720p OCR 后约 264 MiB。SDK 首次加载约 3 秒，预热后取用模块几乎不耗时。

这些不是逐对象堆分析结果。实验使用 offscreen Qt、空数据及禁用系统集成的窗口，不能代表真实屏幕缩放和真实数据的完整启动过程。真实入口 `main.py` 的 `_ensure_deps()` 还会提前导入 OpenAI、BeautifulSoup 等包，其依赖与 SDK 存在交叉。因此约 96 MiB 是当前实验顺序的增量，不能保证改掉 LiteLLM 就净省同样多的内存，也不能把约 145 MiB 差额全部算成缓存或泄漏。

## 3. 第一阶段：建立真实基线，定位差额

优先级最高。先交付开发者诊断入口和可复测报告，不改变普通用户默认行为。

### 采样范围

在真实启动路径记录以下阶段的耗时、进程树专用工作集、专用提交及线程数：

1. Python 启动、依赖检查完成。
2. Qt/Fluent 导入完成、首帧显示。
3. 上下文分词器初始化完成。
4. SDK 与 OCR 各自预热完成。
5. 第一次划词、截图、OCR 结束。
6. 窗口关闭至托盘并空闲 2 分钟。

补充操作场景：连续 20 次截图后取消、重复打开关闭笔记/设置、在同一批会话间切换、加载含图片的会话。分别测量干净临时数据与用户现有数据；不记录内容、路径或密钥。

每个场景用新进程重复三次，记录应用提交号、窗口尺寸、屏幕缩放、数据规模及采样时刻。平台缓存和临时峰值单独说明。

### 检查重点

- 截图层的全桌面 `_frozen` 位图、工具栏和信号引用是否在结束后释放。当前 `closeEvent()` 未显式清空该位图，是待验证的检查点，不是已确认泄漏。
- QPixmap 原图缓存、缩略图、淡入淡出快照和关闭的窗口是否仍被引用。
- 会话切换后的旧消息控件是否完成延迟销毁；会话数据加载和渲染对象各占多少。
- OCR 推理缓冲和 Python/原生分配器保留内存，与仍存活的业务对象区分开。
- `_ensure_deps()` 是否造成没有使用相应功能也导入大型依赖。

验收：给出真实启动到空闲的基线图、重复操作趋势以及可复现的主要增量来源。若仍无法解释，明确保留未归因项，不强行按模块分配。

## 4. 第二阶段：收紧对象生命周期和启动依赖

基于第一阶段证据，先修正低风险项目：

- 在截图动作、取消和异常退出路径中，统一释放已结束的截图缓存及窗口资源；涉及 OCR 后台工作时，保证任务使用的独立图像仍有效。
- 为图片缓存设总字节预算和淘汰机制，而不是只限制条目数。发送中的附件和当前显示内容不能被错误失效。
- 明确会话切换与窗口关闭时的所有者，清理旧控件、临时快照和信号引用。
- 将启动依赖检查改为轻量可用性检查；实际功能首次使用时再报告导入/版本错误，不在启动阶段为检查而初始化整个包。

验收：预热后重复相同操作，处理延迟销毁并空闲后，第二轮相对第一轮的专用提交增量暂以不超过 10 MiB 为排查门槛；出现增长时报告原因。最终门槛根据第一阶段噪声校准，不把正常有界缓存当作失败。

这一步收益取决于实际存活对象，暂不承诺节省多少 MiB。

## 5. 第三阶段：常用供应商使用轻量适配器

目标：减少日常聊天必须常驻的 SDK 和依赖，同时维持快速首次响应。

### 推荐设计

- 继续使用现有 `LLMGateway` 和 `ProviderAdapter` 协议。限流、重试、取消、错误分类、usage 与成本记录留在统一网关。
- 给已验证的 OpenAI 兼容协议新增基于 httpx 的流式适配器，先覆盖当前实际使用的 DeepSeek，再扩大到经过兼容性验证的供应商。
- 路由使用明确的供应商/协议配置，不能只根据 URL 或模型名猜测协议。
- 最终决策：完成替代后彻底移除 LiteLLM，不长期维护双体系。不支持的协议显式报错，不能静默丢内容或重发。
- 无 SDK 可预热，移除旧预热入口；默认不发送探测或推理请求。
- HTTP 客户端按网关生命周期复用，关闭时释放；连接池复用与本地 SDK 预热分别测量。

### 必须保持的行为

文本与 reasoning 增量、跨片段工具参数、usage/缓存 token、图片消息、DeepSeek 参数、HTTP 错误与限流、流中断与取消。无 usage 时保持未知，不补成零；已经输出内容后不重试整个请求。服务端明确完成、异常断流与空结果继续区分。

验收：用受控流式响应做协议契约验证，并复用独立离线评估用例。真实供应商回归按需运行并单列 token 成本。只有验证覆盖的供应商启用新路线。

收益：约 96 MiB SDK 实验增量是候选优化空间上界参考；扣除共享依赖和新适配器后，以真实入口净下降为准。SDK fallback 已删除；新 asyncio 连接池的净收益需以相同条件重新测量。

## 6. 第四阶段：OCR 改为可回收的独立进程

适用于前面优化后，OCR 仍是重要常驻来源的情况。

- 把 RapidOCR、ONNX Runtime 和相关图像依赖放在专用 worker；父进程只持有轻量请求/结果接口。
- 可以保留启动后的后台预热。任务完成后空闲约 120 秒退出 worker；再次需要时重新启动，避免模型和原生分配器长期常驻。
- 用明确状态机管理未启动、加载中、就绪、忙碌和失败。并发请求共用一次初始化，工作中的进程不能被空闲计时器结束。
- 限制任务排队数量、图片尺寸、超时及 IPC 消息大小。协议只允许本应用定义的数据，不执行任意指令。
- 处理打包后的 Windows spawn/freeze_support、崩溃重启和应用退出；不通过公开端口提供服务。
- 初版只提供开发配置调整空闲时间，不增加复杂的用户设置项。

验收：worker 回收后，整个进程树的专用提交明显下降；空闲时没有遗留 OCR 进程。返回结果与当前 OCR 路径一致。已预热 OCR 的响应时间不明显退化，冷启动成本独立记录。

权衡：回收后第一次 OCR 会重新加载，历史构造耗时约 0.5–0.9 秒，另有进程和 IPC 开销，以实现后实测为准。不能同时承诺始终零冷启动和始终零 OCR 常驻内存。

## 7. 分词器与会话数据：按证据后置

分词器约 32 MiB，首次精确计数后仍有价值，不以粗略字符计数替代现有 token 预算约束。可在首次真正需要时初始化，避免纯笔记使用场景付出此成本；这主要降低启动占用，不作为使用后的永久节省。

会话数据样本总文件大小约 1.22 MiB，暂不优先建设复杂的数据库懒加载。若第一阶段发现渲染对象或大量会话实际占用显著，再分别处理消息控件虚拟化与历史数据按需读取。

## 8. 顺序、目标与交付

推荐顺序：第一阶段测量 → 第二阶段生命周期 → 第三阶段轻量适配器 → 根据结果决定第四阶段 OCR 进程化。

候选体验目标：在固定数据、屏幕、路由及空闲条件下，争取将当前约 400 MiB 的专用工作集降到 250–300 MiB。该目标不是已确认收益，第一阶段后需用真实基线修订；同时要求进程树专用提交下降，不能只把主进程的占用挪出去。

性能约束：保留 OCR 等必要的本地准备，移除 SDK 预热；用受控网关测量划词调度与本地准备时间，优化后 p95 增量暂以 100 毫秒为门槛。真实模型 TTFT 单独测量，不把网络或服务端波动算成本地处理退化。

每阶段单独提交实现、测量报告与必要的生命周期/协议验证。每个变更可独立回退。第三阶段不再提供 LiteLLM 回退；OCR 进程化只在总占用收益与稳定性都达标后替换现有服务。

本方案不把发布包体积、磁盘模型大小或 Python 启动器数量作为内存优化的替代指标；也不通过强制 GC 或 Windows 工作集清理来代替对象生命周期治理。
