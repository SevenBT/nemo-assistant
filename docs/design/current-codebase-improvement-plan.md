## 1. 目标与结论

本轮审查关注以下问题：

- 是否存在可确定复现的安全边界或数据可靠性缺陷；
- UI、后台任务、Agent 与持久化之间的生命周期是否清晰；
- 测试、CI、打包和依赖检查能否阻止回归；
- 哪些性能问题值得测量后再优化；
- 哪些结构性债务已经产生真实维护成本；
- 哪些部分方向正确，不应为“重构”而重写。

总体结论：当前分层方向合理，不需要推倒重写。`LLMGateway`、`ToolRegistry`、Prompt Builder、Agent Hook、业务数据库与 Trace 数据库分离等边界应保留。当前优先级最高的不是新增架构，而是封闭工具执行和路径边界、保证敏感数据与会话持久化安全、建立统一后台任务生命周期，并补齐测试与发布质量门。

建议总顺序：

1. 先修测试隔离，确保后续验证不会触碰业务数据；
2. 修复确定性的路径越界和工具禁用绕过；
3. 收紧调用参数、Trace、网络读取和敏感工具授权边界；
4. 治理 Session、SQLite、Agent、评测和退出流程的一致性；
5. 先埋点再做 UI 与网络性能优化；
6. 行为稳定后再拆分大模块。

## 3. 当前架构判断

当前主要数据流为：

```text
main.py
  ├─ 配置、keyring、路径和服务初始化
  ├─ SessionManager（JSON）/ NoteManager（SQLite）/ SchedulerManager
  └─ MainWindow
       ├─ 聊天、截图、划词、便签、托盘等 UI 控制器
       ├─ LLMGateway → LiteLLM
       ├─ ToolRegistry → 内置工具 / 用户脚本工具
       ├─ AgentLoop（QThread）→ 状态机 → 工具执行
       ├─ ConversationPromptBuilder / Consolidator / Dream
       └─ TraceStore（SQLite）/ Eval
```

值得保留的部分：

- UI、核心服务、工具、数据模型总体分层明确；
- LLM 请求、重试和流式输出已集中到统一网关；
- 工具通过统一 Registry 暴露给 Agent；
- Trace 与业务数据分库，方向正确；
- 会话文件采用临时文件替换，具备原子写入基础；
- 聊天流式渲染已有合并窗口；
- 截图 OCR、调度器和主要 Agent 工作已放到后台线程；
- 发布工作流已有版本、标签、Changelog、归档白名单和 SHA256 校验。

当前主要薄弱点：

- “工具是否可见”和“工具是否允许执行”没有统一为一个执行策略；
- UI、后台任务和持久化之间共享可变状态，缺少稳定快照；
- Agent 核心同时承担业务状态机和 Qt 线程职责；
- 部分安全与配置契约只在文档或 UI 层成立，执行层没有强制；
- 测试数量较多，但核心工具、设置页、主窗口和打包产物覆盖不足。

## 4. P0：执行前优先完成

### PR 0.1：隔离测试数据库

**性质：静态确认；复杂度：低；风险：低。**

证据：`tests/test_tags.py:18` 使用无路径参数的 `DatabaseManager()`，后续执行创建、删除和 purge；同仓库其他数据库测试已使用 `tmp_path`。

改造范围：

- 为数据库测试提供统一临时数据库 fixture；
- 禁止测试进程连接仓库默认 `data/` 业务数据库；
- 检查其他依赖默认配置目录、会话目录和任务文件的测试；
- 重写或删除整体跳过且引用旧 API 的 `tests/test_edge_snap_width.py:15`。

验收：

- 全套测试前后，默认业务数据库、会话、任务和配置文件均无变化；
- 测试尝试连接默认业务路径时立即失败并给出明确原因；
- 现有 336 项通过结果不回退。

依赖：无。此 PR 应先于所有其他改造。

### PR 0.2：修复 workspace 路径边界

**性质：已验证；复杂度：低；风险：低。**

证据：`app/tools/_path_utils.py:42` 使用字符串 `startswith()` 判断目标是否位于 workspace。若 workspace 为 `.../Documents`，相邻目录 `.../Documents-secret` 会被误判为子目录。该 helper 被文件读取、目录遍历、搜索和 `exec` 工作目录检查复用。

改造范围：

- 改为路径组件级包含关系；
- 明确 workspace 本身是否合法；
- 在 Windows 上覆盖大小写、盘符、UNC、符号链接和 junction；
- 所有文件类工具共用同一组参数化边界测试。

验收：

- `..`、绝对路径逃逸、同前缀兄弟目录、junction/symlink 逃逸全部拒绝；
- workspace 本身和真实子目录继续可用；
- 错误类型和用户提示一致。

依赖：PR 0.1。

### PR 0.3：统一工具执行策略

**性质：已验证；复杂度：中；兼容风险：中。**

证据：`app/tools/registry.py:188` 只在导出模型工具列表时过滤 `enabled`；`app/tools/registry.py:226` 的执行入口未检查启用状态。`app/core/scheduler.py:118` 可直接通过该入口执行任务，因此已关闭或默认关闭的工具仍可能被计划任务或内部调用执行。

改造范围：

- 在唯一执行边界检查：存在性、启用状态、可用状态、风险级别、调用来源和后台可调度性；
- Agent、调度器、评测和手动测试均使用同一策略入口；
- 创建任务和任务触发时分别校验；
- 对历史失效任务保留记录并显示错误状态，不静默删除；
- 评测默认使用无真实副作用的工具策略。

验收：

- disabled/unavailable 工具从任何普通入口都无法执行；
- 工具创建任务后再关闭，任务触发时被明确拒绝；
- 临时授权必须显式、可审计且不改变持久化全局开关；
- 拒绝结果可被 UI 和 Agent 正确展示。

依赖：PR 0.2。

### PR 0.4：分离公开参数与内部执行上下文

**性质：静态确认；复杂度：中；兼容风险：中。**

证据：`app/core/agent_loop.py:456` 和 `:479` 会把 `_session_id` 原地写入模型生成的参数；同一参数对象可能经工具事件写入会话，并在后续轮次再次发给模型。`ToolCallView` 虽为 frozen dataclass，但其中的 `arguments` 仍是可变字典。

改造范围：

- 引入不可变的 `ToolInvocation`，分为 `public_arguments` 与 `execution_context`；
- Hook、UI、会话、checkpoint 和 trace 默认只能看清洗后的公开参数；
- 内部 session、trace、授权和调用来源信息不得混入模型参数；
- 对历史会话中的内部字段做兼容过滤；
- 递归冻结或深拷贝传给 Hook 的参数快照。

验收：

- Hook 无法原地改变审批后实际执行的参数；
- 会话 JSON 和下一轮模型消息中不出现 `_session_id` 等内部字段；
- Memory 等依赖 session 上下文的工具仍可通过私有上下文工作。

依赖：PR 0.3。

### PR 0.5：递归脱敏 Trace 与日志

**性质：已验证；复杂度：中；兼容风险：中。**

证据：`app/core/trace_store.py:776` 仅检查顶层参数键名；`app/core/trace_store.py:353` 将工具结果直接写入数据库。嵌套对象、Authorization、Bearer token、URL query、剪贴板和文件内容可能明文落库。

改造范围：

- 建立共享递归 sanitizer，覆盖参数、结果、错误、Header、URL 和日志字段；
- 支持按工具声明记录策略：完整结构、摘要、长度或完全不记录正文；
- 文件、剪贴板、笔记和记忆等敏感读取默认不记录正文；
- 提供历史 Trace 清理或迁移说明；
- 日志中保留诊断上下文，但不记录 prompt、密钥和原始敏感正文。

验收：

- canary secret 在 `traces.db`、JSONL、错误信息和安全事件中均不可检索；
- 嵌套 dict/list、大小写键、Bearer、URL query 和命令行 token 均被处理；
- 非敏感结构、状态、耗时和长度仍可用于回放与评测。

依赖：PR 0.4。

### PR 0.6：限制网络读取并闭合超时/取消

**性质：部分静态确认，部分待专项验证；复杂度：高；兼容风险：中高。**

证据：`app/tools/fetch_url.py:145` 使用普通 `client.get()` 缓冲完整响应，直到解析后才截断文本；URL 安全检查和实际连接分别解析 DNS。`app/core/llm_gateway.py` 定义了超时配置，但需验证所有 LiteLLM 路径是否实际使用。

改造范围：

- `fetch_url` 使用 streaming，限制实际下载字节和解压后大小；
- 提前检查 Content-Type 和 Content-Length，但不能依赖它们作为唯一限制；
- 每次重定向重新执行地址策略；
- 设计与连接阶段一致的 SSRF 校验，兼容代理、CDN、多地址域名和 TLS SNI；
- 让取消可中断限流等待、重试等待和长 `Retry-After`；
- 明确连接、读取和整轮 LLM 的独立超时。

验收：

- 超大、chunked、gzip 和无 Content-Length 响应达到限制后立即关闭；
- DNS 重绑定、IPv4-mapped IPv6 和非公网地址被拒绝；
- 用户取消后在限定时间内结束且不再发起重试；
- 常见代理、CDN 和兼容 API 网关继续工作。

依赖：PR 0.3。SSRF 连接策略应先写技术验证，不应直接以“域名换 IP”实现。

## 5. P1：数据与运行可靠性

### PR 1.1：版本化 SQLite 迁移与外键完整性

**性质：静态确认；复杂度：中；风险：中。**

证据：`app/core/db_manager.py:45` 声明多处 `ON DELETE CASCADE`，但 `app/core/db_manager.py:27` 创建连接后没有启用 `PRAGMA foreign_keys=ON`。当前迁移依靠逐列检查，笔记 HTML 转 Markdown 还可能在启动时扫描全库。

改造范围：统一连接工厂，设置 foreign keys、busy timeout 和 WAL；用 `PRAGMA user_version` 建立顺序迁移；迁移前检测并处理孤儿记录；把 HTML 转换改为一次性、可回滚的迁移。

验收：旧数据库 fixture 可幂等升级；级联删除真实生效；损坏或未知版本不静默继续；迁移失败保持原库可恢复。

### PR 1.2：原子化 SessionStore

**性质：静态确认；复杂度：中高；风险：中。**

证据：`app/core/session_manager.py:46` 在锁外序列化会话；消息 append 和部分字段修改也发生在锁外。较旧快照存在最后写入并覆盖较新数据的窗口。现有并发测试只验证 JSON 可解析，没有验证消息完整数目。

改造范围：以命令式 API 收口 `append`、`replace_tail`、`finalize_turn`、归档和删除；在同一锁内完成内存变更、不可变快照和原子替换；查询返回快照而非可任意修改的内部对象。

验收：并发追加后磁盘消息数量和顺序完整；编辑、重生成、压缩和归档不丢数据；写盘失败不把内存状态伪装为已保存。

### PR 1.3：修复 Agent 最终结果与评测闭环

**性质：静态确认；复杂度：中；风险：中。**

证据：`app/eval/runner.py:102` 运行 Agent 时不挂 Eval Hook，但 `app/eval/runner.py:186` 又从 Hook 写入的 sample 中读取最终回答。Agent 完成信号没有把最终文本作为明确结果返回。

改造范围：定义 `TurnResult(final_text, tool_results, error, trace_id, status)`；聊天和评测都消费该结果；TraceStore 只负责观测，不再充当功能返回通道。

验收：假网关端到端测试中，最终回答、规则评分、Judge 输入和数据库结果非空且一致；失败和取消不会产生伪成功样本。

### PR 1.4：统一后台任务生命周期

**性质：静态确认；复杂度：高；风险：高。**

证据：`app/core/agent_loop.py:66` 同时承担状态机和 QThread；`app/ui/main_window.py:780` 退出时只发取消，不等待 worker；`app/ui/tool_test_dialog.py:168` 使用 `QThread.terminate()`；Dream 和调度任务也没有统一所有者。

建议分两步实施：

1. 先建立 `TaskSupervisor`，统一登记、停止接单、取消、限时等待和退出报告；
2. 再将纯同步 `AgentRunner` 与 Qt Worker Adapter 分离，不重写现有状态机语义。

验收：退出时运行慢工具、LLM stream、Dream 和 scheduler job，不出现残留线程、`QThread destroyed` 警告或未落盘状态；总等待时间有明确上限。

### PR 1.5：把 turn 准备阶段移出 UI 线程

**性质：高可信性能候选；复杂度：高；风险：高。**

证据：`app/ui/chat_session_controller.py:399` 在启动 Agent worker 前同步执行历史压缩和 Prompt 构建；`app/core/consolidator.py:106` 可能同步等待完整 LLM 请求；`app/core/conversation_prompt_builder.py:136` 会读取、缩放、编码图片或执行 OCR。

改造范围：以不可变会话快照执行“压缩、图片/OCR、Prompt 构建、Agent 启动”；准备结果回主线程时校验 session id 和 revision；支持取消和切换会话。

验收：长会话、图片历史和 vision-off OCR 场景下 UI heartbeat 不出现超预算停顿；取消准备不会启动后续 LLM；快速发送、编辑、删除和切换会话不会串线。

依赖：PR 1.2、PR 1.4。

### PR 1.6：稳定 Registry 与运行时配置语义

**性质：静态确认；复杂度：中；风险：中。**

证据：聊天、评测和调度共享可动态修改的 Registry，而 Registry 没有稳定快照；部分工具在构造时缓存 provider、保存目录或 API key，设置更新后可能必须重启才生效。

改造范围：Registry 使用 copy-on-write/versioned snapshot；一个 turn 固定使用启动时的工具集合；业务配置保存后原子重建工具快照，主题预览等 UI 配置保留即时语义；设置取消不应保留业务配置副作用。

验收：运行中刷新工具不影响已开始 turn；新 turn 使用新配置；取消设置不会改变搜索源、目录或密钥引用。

### PR 1.7：明确 checkpoint 产品语义

**性质：静态确认的未闭环能力；复杂度：中；风险：高。**

证据：`app/core/checkpoint.py:60` 提供恢复函数，但仓库没有调用恢复；公开文档声称异常后可恢复。

待维护者选择：

- **保留并完成**：只恢复已完成结果，未完成调用标记 interrupted，绝不自动重放有副作用工具；
- **移除**：删除无调用的写入逻辑和公开承诺。

验收取决于选择。保留时必须覆盖崩溃、损坏文件、重复启动、取消和副作用不重复执行。

### PR 1.8：收敛用户工具 manifest 契约

**性质：静态确认的未闭环能力；复杂度：中到高；风险：中高。**

证据：工具编辑器提供 `ai/config/manual` 三种参数来源，但脚本适配器向脚本发送空 context；manual 输入缺少完整发起链路。

待维护者选择：

- 近期只支持 `ai` 参数并隐藏未实现选项；
- 或正式实现 Manifest Compiler、配置/keyring 参数解析和 manual 输入状态机。

在秘密参数解析和审批机制完成前，不应让 UI 暗示这些来源已可用。

## 6. P2：先测量再实施的性能改造

第一步不是重构，而是建立统一性能基线。建议记录：

| 指标 | 建议场景 |
| --- | --- |
| 主线程最大 stall、p95/p99 stall | 长对话、切会话、打开设置、截图 |
| 点击发送到 Agent 启动 | 普通对话、需要压缩、含历史图片 |
| 单次流式渲染耗时和累计次数 | 长 Markdown、表格、代码块 |
| 会话切换到首帧 | 100/500/1000 条消息 |
| 启动到首个可交互窗口 | 冷启动、已有大量会话/笔记 |
| 峰值 RSS | 多屏截图、长会话、大网页 |

测量确认后按以下顺序考虑：

### 2.1 图片与 OCR 缓存

`app/core/conversation_prompt_builder.py:38` 每轮遍历历史；图片可能重复读取、解码、缩放、base64 或 OCR。缓存键至少包含规范路径、大小、mtime、目标尺寸和编码参数，并设置容量与失效策略。

### 2.2 长会话渐进或窗口化渲染

`app/ui/chat_widget.py:656` 切换会话时销毁旧气泡并重建全部历史。只有在长会话基准确认明显停顿后，再采用按视口渐进构建或窗口化；必须保留滚动锚点、工具卡片和操作目标。

### 2.3 流式 Markdown 尾部渲染

当前已有约 40 ms 的合并窗口，但 `app/ui/chat_widget.py:84` 仍会对累计全文反复 Markdown 转换和布局。可以先根据单次渲染耗时自适应调节刷新间隔；进一步优化时，仅更新未闭合尾块，终态再完整渲染。

### 2.4 网页工具连接复用

确认 DNS/TCP/TLS 建连占比后，再为 Web Search/Fetch 注入有明确生命周期的共享 `httpx.Client`。该项必须与 PR 0.6 的 SSRF 和退出策略一起设计。

### 2.5 笔记搜索扩展

当前 LIKE 搜索和列表重建在大量笔记时可能退化。用 1k/10k/50k 数据量测量后，再决定是否引入 FTS、分页、结果上限和批量文件夹查询。

### 2.6 打包体积

当前 PyInstaller 对多个大型依赖使用 `collect_all`。先用 TOC/import graph 和冻结 EXE 冒烟确认真实模块，再改为精确收集，并设置 ZIP 体积预算。

## 7. P2：工程化与发布质量门

### PR 2.1：覆盖率增量门禁

当前总覆盖率约 31.69%，不能直接把全局门槛一次抬到 80%。建议：

1. 先锁定全局覆盖率不得低于当前基线；
2. 要求变更代码覆盖率不低于 80%；
3. 优先补 AgentLoop、配置迁移、TraceStore、高风险工具、主窗口启动和设置页；
4. 分阶段把全局门槛提高到 50%、65%，最终目标 80%。

### PR 2.2：冻结 EXE 自动冒烟

当前打包 CI 主要检查 EXE 存在，真正启动仍依赖人工 release checklist。增加 `--smoke-test` 或专用入口，在冻结环境初始化 QApplication、配置、工具发现和主窗口后自动退出；检查退出码、crash.log 和 PyInstaller warnings。

### PR 2.3：OCR/Python 3.12 兼容性

解决 `rapidocr-onnxruntime 1.2.13` 包元数据与 Python 3.12 的冲突。选择明确支持 3.12 的版本，或重新评估项目 Python 基线；Windows CI 使用固定小图执行一次真实 OCR，不能只 mock。

### PR 2.4：Lint、类型与依赖门禁

- Ruff 先阻断 `F821/F811/F841` 等高信号规则，再逐步扩大；
- 类型检查先覆盖 `core/tools`，清零后再扩展 UI；
- CI 增加 `uv pip check` 和依赖漏洞扫描；
- 依赖例外必须记录漏洞编号、理由和到期日；
- 测试 workflow 与发布 workflow 使用一致、固定版本的 uv 和 Action SHA。

### PR 2.5：日志与故障采集

增加 rotating file handler、`threading.excepthook` 和 Qt message handler；日志记录版本、OS、trace id、组件和异常类型，但必须经过 PR 0.5 的脱敏器。

## 8. P3：行为稳定后的维护性改造

以下项目有真实维护成本，但不应先于 P0/P1：

### 3.1 Agent 事件 DTO

逐步用 `SessionRunState`、`ToolEvent`、`RunResult` 等 dataclass/TypedDict 替代跨线程裸 dict 字段协议，减少字段拼写、缺失和 stale state 问题。

### 3.2 Notes 子系统拆分

`NotesPanel`、`NoteManager` 同时承担 UI、编辑、搜索、文件夹、标签、待办、迁移和便签状态。待迁移和行为测试稳定后，按 `NoteRepository`、`FolderService`、`SearchService` 和 UI 子控制器拆分。

### 3.3 TraceStore 拆分

保留遥测写入 best-effort，但查询失败不能继续伪装成空结果。拆分 schema/migration、writer、query repository 和 eval repository；查询返回受控错误。

### 3.4 配置单一来源

当前运行默认值、示例配置、迁移字段和主题选项存在多个事实来源。建立配置 schema/default registry，由它驱动 validator、示例和迁移；主题列表从主题注册表派生。

### 3.5 无边框 resize 复用

两个浮窗存在近似 resize 状态机。由于 Qt 全局事件过滤和窗口行为敏感，只在行为测试、DPI 和多屏回归齐备后抽取参数化 controller。

### 3.6 清理半实现或不可达能力

标签/待办 UI、PDF 依赖、wheel 交付和其他不可达能力先做产品确认。要么形成完整入口和端到端测试，要么删除残留代码、依赖和文档，避免维持“模型存在但用户不可达”的状态。

## 10. 明确不建议的改造

- 不引入微服务、CQRS、事件总线、Redis 或远程数据库；这是单用户桌面应用，当前问题是进程内边界和生命周期。
- 不替换 PyQt6、qfluentwidgets、Qt signal/slot 或现有无边框窗口方案。
- 不合并 `notes.db` 与 `traces.db`；业务数据和观测数据分库是合理边界。
- 不移除 `LLMGateway`、`ToolContext`、Prompt Builder、Hook 或 Registry；应强化其契约，而不是重建一套。
- 不把所有 UI 状态强制改成不可变对象；不可变快照应优先用于 UI→任务、任务→持久化、公开参数→私有上下文边界。
- 不仅因为文件行数较大就机械拆文件；先通过测试锁定行为，再按真实职责拆分。
- 不在没有 profiler 或基准数据时优化 resize 事件过滤、OCR 行分组、主题切换等低频路径。

## 12. 全局完成标准

一项改造只有同时满足以下条件才算完成：

- 对应问题有先失败后通过的回归测试；
- `uv run python scripts/check_repo.py` 通过；
- `uv run pytest -q` 通过；
- 变更代码覆盖率不低于 80%，全局覆盖率不下降；
- 涉及打包、Qt 生命周期或 Windows 平台行为时，有冻结 EXE 或实机验证；
- 涉及工具、文件、网络、密钥、Trace、调度时，通过安全审查；
- 不修改无关行为，不把多个独立任务塞入同一 PR；
- 用户可见行为、迁移和兼容变化更新对应文档。
